# 可证伪创新方向库

这些不是“保证发表”的点子，而是从本地卡片和调研报告中提炼出的候选研究问题。每个方向必须先通过基线和消融验证。

| 方向 | 现有瓶颈 | 可组合模块 | 最小可证伪实验 | 必须报告 |
| --- | --- | --- | --- | --- |
| 不确定性感知安全控制 | 预测/状态分布外时 RL 可能输出不可行动作 | 概率预测 + OOD 检测 + 动作投影/安全 MPC | 在未见 PV/负荷和噪声下比较无门控、惩罚、投影 | 成本、违例率、严重度、拒绝率、延迟 |
| 多时间尺度协调 | 日前计划与实时控制目标不一致 | 日前 MILP/随机优化 + 日内 MPC + 实时策略 | 相同场景下比较单层与分层方案 | 计划偏差、计算时间、SOC 终端误差 |
| 安全多 Agent 协同 | 局部观测和通信延迟导致非平稳 | 集中式 critic + 分散执行 + 安全协调器 | 延迟/丢包/局部观测压力测试 | 通信量、恢复时间、最坏违例 |
| 世界模型与数值校验 | 学习模型快但不一定忠实于潮流 | 学习 surrogate + AC/OPF oracle + 置信度门控 | 只在高置信度时使用 surrogate，其他回退求解器 | 校准误差、回退率、端到端延迟 |
| LLM 工具编排 | 文本规划不能直接成为控制量 | 结构化工具 schema + 求解器 + 人工审批 | 比较自由文本、结构化调用、无 LLM 三种流程 | 工具调用正确率、幻觉率、约束通过率 |
| 面向操作员的可解释性 | 平均 reward 难以支持实际信任 | 反事实分析 + 证据引用 + 失败回放 | 同一故障下比较解释前后人工决策质量 | 解释延迟、错误接受率、工作负荷 |

## 研究闸门

1. **问题闸门**：是否明确任务、时间尺度、观测和动作，而不是泛泛谈“智能调度”？
2. **基线闸门**：是否包含规则/随机、优化或 MPC、标准 RL 中至少两个适用基线？
3. **安全闸门**：是否记录 proposed action、accepted action 和拒绝原因？
4. **证据闸门**：是否能从原文或运行 artifact 追溯每个 claim？
5. **复现闸门**：第三方是否可以用固定配置、种子和版本重跑？
